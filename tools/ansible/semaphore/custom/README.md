## 发布异常处理（本轮）

- `POST /operations/{id}/reconcile` 需要原生任务执行权限及 `If-Match`，仅提交既有只读检查任务；同设备检查合并。配置原生定时检查后，也会补查被该设备占用的原事务。
- 下级只读 `release_probe.py` 依据管理员固定 profile 查找原报告，校验操作、原任务、设备与主机身份。最终报告缺失时，仅在绑定完整、验收/收尾已确认且主机完成标记一致时重建结果；不改写目标机状态，不执行或重投发布。
- 原生发布任务未终结时不释放占用。原任务终结且全部目标的结果得到确认后，平台事务更新结果并释放锁；未知、恢复失败或未完成维护仍保留占用。没有最终证据不是“未执行”的证明。
- 本地 systemd 启动失败须再次确认服务已停止、无挂起启动作业；下级启动失败须核对同一请求的明确失败结果、零 PID、无 pending 及原维护归属，才能进入兼容性受限的二进制恢复。网络回复不明不盲目回退。
- 新 Agent 确认启动失败时，不再调用其已不可用的 HTTP 接口排空；必须先核对持久化维护身份、已停止下级和 `/proc` 无残留进程，才允许恢复原程序。
- 已停止 Agent：持有实际 `agent.lock`，校验持久停止状态、未完成请求/维护及 `/proc` 映像；整个升级不启动 Agent/下级、不改状态文件或维护代次。无法取得足够进程证据时拒绝安装。
- 只读检查缓存适配器与实际数据格式。`GET /packages/{id}/compatibility` 和组件历史提前显示禁用原因；恢复历史分页 20/50/100，检查包完整性、版本依赖、架构、过期状态及数据格式。执行时再次校验，不能凭缓存跳过检查。
- 页面提供“补查原事务”，错误使用安全的原因码和中文说明，不显示原始异常中的配置或凭据；设备详情向历史组件传递原生权限，不再误隐藏恢复按钮。

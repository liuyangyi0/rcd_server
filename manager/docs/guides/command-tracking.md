# 命令全链路记录

## OPC 连续下发与结果读取

同一管理端对固定来源＋物理串口的`_Send`/组`Send`变量写入采用FIFO，容量64条（含执行中）；相同载荷不合并，队满返回`BadWaitingForResponse`。同步`SendCommand` Method不入队，有执行或排队命令时返回占用。队列不在三台管理端之间共享，跨管理端竞争仍由下级端口互斥拒绝。
客户端必须检查每项 Write 返回值；`Good` 只表示受理，不是设备动作成功。
`_Send`与`Groups/<组ID>/Send`保留`2`未终止（可能排队或等待ACK）、`1`收到ACK、`3`失败及原有坏质量语义；阶段细分看队列计数与命令记录state。
管理端在释放端口前将每次终态的独立快照送入发起 Session 的监控队列；连续相同结果不再依赖采样捕获中间的 `2`。
这不是无限事件日志：客户端仍需配置足够的 MonitoredItem QueueSize（连续操作建议至少 16），
队列溢出或断线超过保留窗口应核对命令审计，不能据此自动重发硬件命令。

只处理 Good 值的客户端可读取/订阅只读 String 节点：
`ns=3;s=Groups/<组ID>/CommandResult`。它按 Session 返回最近命令的 JSON 结果：
`command_id`、`state`（Received/Failed/TimedOut）、`status_code`（数字）、`error`。
此节点的 Good 仅表示结果报告有效，失败/超时仍由字段明确表示；没有完成结果时为
`BadWaitingForInitialData`。新命令发起后等待其新结果，不能把旧编号当成本次成功。
不同Session不共享历史。`CommandResult`是最近终态快照，不是全部排队命令的结果日志；连续下发逐条核对须使用command_id及命令审计，不能用最新终态替所有请求确认。旧业务NodeId、类型及Method签名不变。

命令总期限包含排队时间。下级明确返回终态失败（包括ACK超时）后可以继续下一条；管理端失联、等待超时或执行结果不明时终止剩余队列，不盲目派发。管理端重启不重放队列，来源与连接代次在接受时固定。

关联协议中的 `ack_timeout` 映射为 `TimedOut/BadTimeout`；等待超时不重投。
下级接收下一条前仍检查实际串口执行许可；已完成但尚未被 ACK 定时任务清理的记录
不会额外占用一个刷新周期，旧 ACK 也不能清除或覆盖新命令。

## 从 Web 查看

在“命令记录”中点击某一行的“执行过程”。支持关联协议的下级会显示来源、物理串口、管理命令编号、下级编号、实际发送次数、完整写出次数、每次 ACK 等待结果和最终结果。

- “调用发送 3 次、完整写出 2 次”表示有一次发送未确认完整写出，不能说设备只接收到两次。
- “收到设备 ACK”表示下级收到协议 ACK，不等于设备动作反馈已经得到核实。
- 管理请求超时后补查到成功，显示“随后确认收到 ACK”，原超时结论保留。
- 审计降级、缓存淘汰或缺口会明确提示记录不完整。缺少下级记录时显示未知，不猜成零次或失败。
- “执行快照已取得，历史同步曾有缺口”表示已读到原下级的执行摘要及累计发送次数，但管理端不保证保存了每个中间变化事件；与下级自身标记的“审计记录不完整”不同。历史缺口不会被补查摘要悄悄抹掉。
- 旧下级、历史记录和直接连接下级的独立命令不按时间、相同报文强行关联；原“串口发送明细”仍保留。

列表仅返回摘要；打开详情才获取完整记录。Web 不新增发送设备命令的按钮。
健康检查和命令页可显示审计故障；审计故障本身不触发自动选源或阻止采集/控制。

## OPC 客户端的行为

原业务 NodeId、`_Send` 字符串写入、`_SendCommand` 参数和返回协议不变。
变量Write成功只表示管理端接受，可能尚未派发给下级；最终协议确认应核对ACK与独立命令记录。同步Method等待终态，只有Good及Result="1"表示收到协议ACK，不证明设备动作反馈已经核实。已经返回的调用结果不会被后来的补查追溯修改。

管理端自动读取下级 Operations v1 的 `command_tracking` 能力。新下级通过独立关联接口接收请求；明确不支持的旧下级继续使用 `_Send`。
新接口超时、连接断开或回复不明确时，绝不自动改走 `_Send` 重发，也不自动换另一来源。

不同管理端具有独立持久化实例编号；同一管理端同一命令编号重复提交不再次入队。新旧接口仍共享物理串口占用，串口只由原 worker 读写。
串口线上仍然是原始报文，ACK 仍是 `00 50 50`。软件编号不能解决物理 ACK 没有命令编号的问题，因此不保证设备恰好执行一次。

## 审计文件与恢复

下级配置目录新增 `command-journal.sqlite`（SQLite WAL）。独立线程写库，串口 worker 只更新内存记录。
冷历史快照查询使用独立的有界只读队列和 WAL 读连接，不排在落盘或保留期清理之后；仍保留约 100 ms 查询预算，并核对数据库格式和下级实例身份。文件不可读、身份不符或查询超时会明确失败，不伪装成“没有记录”。事件游标查询仍由原写入线程协调，避免绕过未落盘事件边界。
正常接收先等接收记录持久化；超过约 100 ms 的确认预算或写入失败后，继续执行并显示审计降级。
下级记录默认保留最近 7 天、最多 100,000 条已结束命令；进行中记录不因保留策略删除。
内存缓存最多 10,000 条，淘汰未补存记录后保留缺口提示。极端多次重试最多保留最近 256 条发送明细，累计次数保留并标记记录不完整，不改变配置中的重试次数。

重启时，下级把未持久化结束结果的历史命令标为“执行中断、结果未知”，不重新入队。
下级实例标识与审计库绑定，与普通日志的 boot ID 无关。写库失败时尽可能只读恢复身份；新库在存储恢复后沿用本进程的实例标识。若启动时旧库完全不可读、恢复后发现属于不同实例，或数据库版本高于当前程序，保持审计降级并提示人工恢复，绝不混写历史记录；采集和控制仍继续。不要通过删除审计库来消除告警，应保留故障库并核对配套备份。
管理端保存目标来源、物理串口、下级设备实例/进程启动编号和请求摘要，按游标补查。执行中约 250 ms 只读补查；空闲来源有 revision 通知及较慢的兜底补查，各来源互不等待。

管理端按有界批次提交执行证据和同步游标，不等待所有来源的内存审计一起落盘。来源级历史缺口只在事件批次提交时标记，不在每条快照补存时反复改写整段历史。已结束但缺少执行快照的命令也会分批只读补查；下级已按保留策略删除的记录仍显示未知，不伪造次数。

修改来源 IP 后，旧命令仍保留原来源 ID、下级实例、启动编号、串口和请求摘要。若当前另一个来源连接到了旧命令固定的下级实例，可通过该连接只读取得旧快照；不会把旧命令重新发送到新 IP，也不把历史记录改绑为新来源。旧下级已不在连接范围或证据已过期时，不能保证补回。

管理端数据库新增命令关联、事件及游标表。普通 HTTP 日志推送失败不会被当成命令失败，也不是判断命令完成的唯一途径。
管理端审计失败时缓存记录、继续控制、释放已结束命令的端口占用；恢复只补存，不再次发送。

升级或回滚前应备份数据库、WAL 一致性状态、配置与二进制。旧管理端拒绝较新 schema；回滚必须使用配套数据库备份，不能只替换 EXE。

## 接口

- `GET /api/v1/commands/{id}`：原管理命令及下级关联快照。
- `GET /api/v1/commands/{id}/events?limit=100&offset=0`：已保存的变化快照。
- 原列表增加 `tracking` 摘要，不移除旧字段；次数字段缺失表示未知。
- 下级只读 `Operations/CommandRevision` 用于通知有记录变化；不是设备完成状态。

精确 JSON 定义与跨语言黄金样例见 [command-tracking v1](../../../contracts/command-tracking/v1/README.md)。

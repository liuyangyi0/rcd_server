# RCD 管理程序使用说明（Linux 版）

版本：`0.4.4-opc-routing`。适用 Linux x86_64 / Kylin V10 SP1；已在远端真实 Rust 下级环境验证；不是 Windows 包。

## 1. 程序与入口

- `RcdManager`：管理程序，内嵌网页；同一二进制以 `agent run` 模式独立守护一个下级，无需安装 Go 或 Node.js。
- `lower/rcd_server`：配套 Rust 下级。程序包不含现场数据库、配置或证书私钥。
- 客户端固定连接管理 OPC `opc.tcp://<管理器IP>:4840`；默认 Web 为 `http://<管理器IP>:8080`。
- Rust 下级 OPC 默认使用 `4841`，不得占用管理器的 `4840`。同一主机有多个下级时，通过 `RCD_OPCUA_PORT` 分配独立端口。

不要重复启动占用既有端口。以下示例用于新安装，替换占位路径与主机名后使用。

## 2. 新机启动与接入

解压 Linux 包，进入包目录核对校验和，再启动管理器：

```bash
sha256sum -c SHA256SUMS
./RcdManager run \
  --data-dir /absolute/path/to/manager-data \
  --opc-listen 0.0.0.0:4840 \
  --opc-advertise-host MANAGER_HOST \
  --http-listen 0.0.0.0:8080
```

前台按 `Ctrl+C` 停止；首次创建数据库、日志与证书，以后沿用同一 data-dir。包内管理器 v3、Rust v1 均为未剥离调试信息的动态链接构建，文件较大；下级需 `libudev.so.1`，其他发行版须核对动态库。包不自动安装服务。

首次配置顺序：

1. 在“分组与选源”建立设备逻辑组及共享兼容组。
2. 在“下级 OPC”添加稳定 Source ID、Endpoint 和连接方式；冗余下级使用同一共享兼容组。当前 Linux 版不支持持久保存下级密码，按已验证方式使用匿名连接。
3. 等目录发现，在“串口 / 设备映射”把各下级对应设备绑定到同一逻辑组。同名 KKS 不能分属不同组；两边完成后核对目录就绪。修改映射前关闭在线 Session，等待命令完成。
4. 设置各组默认来源，上级连接管理 OPC，浏览点位。

下级业务配置在实际可执行文件同级的 `config/`，PKI 依工作目录。未设置环境变量时下级监听 `4841`；显式使用 `RCD_OPCUA_PORT=4842` 等端口时，管理器中的来源 Endpoint 必须同步修改。升级前停止**目标下级**并备份，保留配置、PKI 和实际日志路径；不能让两实例争用串口，不删除锁文件绕过互斥。

## 3. OPC 客户端怎样查找并切换来源（重点）

### 3.1 先理解三个对象

- **KKS 业务变量**在 `urn:SerialServer`（本版本固定 `ns=2`），例如 `ns=2;s=UNIT1_TEMP`。客户程序照常 Read 或 Subscribe 这些变量。
- **逻辑组**在 `urn:RcdManager:management`（本版本固定 `ns=3`）。一个组是一批必须一起选源的 KKS，通常对应一个可独立冗余切换的子站/设备。
- **Source ID**是一个下级 OPC 实例的稳定标识，例如 `lower-a`、`lower-b`。同一个逻辑组可以由多个 Source 提供。

切换单位是“当前 OPC Session 的整个逻辑组”，不是单个 KKS，也不是整个管理器。两个客户端即使都匿名连接，只要是两个 Session，就可以对同一 KKS 选择不同 Source，互不影响。

### 3.2 管理节点表

从 `Objects/RcdManager/Groups/<group_id>` 浏览。以下都是 String NodeId；示例组为 `device-a`：

| 节点 | 类型/权限 | 用途 |
|---|---|---|
| `Groups/device-a/PointNodeIds` | String[]，只读 | 该组当前有效 KKS 的 `ns=2` String NodeId identifier；用于从 KKS 反查组 |
| `Groups/device-a/PointNodeCount` | UInt32，只读 | `PointNodeIds` 元素数；供 SDK 分页读取 |
| `Groups/device-a/PointSetFingerprint` | String，只读 | 点集指纹；值改变后再重新分页读取清单，避免反复轮询大数组 |
| `Groups/device-a/PointSetRevision` | UInt64，只读 | 本进程内点集版本；分页前后必须一致，否则丢弃本次结果并重读 |
| `Groups/device-a/CatalogRevision` | UInt64，只读 | 整个组目录的 seqlock；点表和全部成员读取前后必须为同一个非零偶数 |
| `Groups/device-a/MemberSourceIds` | String[]，只读 | 该组配置的全部候选 Source ID；其中可能包含当前不可选来源 |
| `Groups/device-a/SelectedSourceId` | String，当前 Session 读写 | 当前 Session 给该组选择的 Source；这是切换的唯一写入口 |
| `Groups/device-a/SelectionRevision` | UInt64，当前 Session 只读 | 每次成功写入 `SelectedSourceId` 后递增，用于确认切换确实完成 |
| `Groups/device-a/DefaultSourceId` | String，全局读写 | 只决定以后新建 Session 的初始来源；不要用它切换当前客户端 |
| `Groups/device-a/PendingCommandCount` | UInt32，只读 | 大于 0 时该组正在等待命令结果，暂时禁止切源 |
| `Groups/device-a/Members/<source>/Selectable` | Boolean，只读 | 是否允许选择该来源；选择前必须为 `true` |
| `.../IsSelected` | Boolean，当前 Session 只读 | 该成员是否正被当前 Session 选中 |
| `.../ConnectionState`、`CatalogState` | String，只读 | 下级连接与目录状态 |
| `.../CompleteCoverage` | Boolean，只读 | 该来源是否具有组内全部 KKS |
| `.../CoverageKnown`、`CoverageFingerprint` | Boolean / String，只读 | 覆盖清单是否已知及其变化指纹 |
| `.../CoverageRevision` | UInt64，只读 | 本成员覆盖清单版本；分页前后必须一致 |
| `.../ProvidedPointNodeIds` | String[]，只读 | 该来源实际具有的组内 KKS；用于精确判断某个 KKS 能否从该来源读取 |
| `.../MissingPointNodeIds` | String[]，只读 | 相对当前组并集不可用的 KKS，可能是缺失、热退役或类型/归组不兼容 |
| `.../Ports/<port>/Devices/<station>` | 对象树，只读 | 查看该来源后面的真实串口、子站、地址、名称和 KKS 前缀 |

数组里的 `UNIT1_TEMP` 是 identifier，完整业务 NodeId 为 `ns=2;s=UNIT1_TEMP`。正式 SDK 最好先读 `Server/NamespaceArray`，按 URI 查到 namespace index，不要只依赖数字 2、3。
管理器宣告 `MaxArrayLength=131072`，覆盖约定的 20×5300 点元素数量，但完整响应仍受 OPC 客户端协商消息大小限制。生产客户端应默认分页：先读对应 Count，再在 ReadValueId 的 `IndexRange` 中按 `0:999`、`1000:1999` 分页；单元素范围如 `5299:5299` 也受支持。`ProvidedPointNodeIds`、`MissingPointNodeIds` 的总数分别由 `ProvidedPointCount`、`MissingPointCount` 给出。
单个数组分页必须使用稳定版本协议：先读 `PointSetRevision=R1`，读取 Count 和全部页面，再读 `PointSetRevision=R2`；仅当 `R1=R2` 时接收结果，否则丢弃并重试。成员清单同样在分页前后读取 `CoverageRevision`。这些变量由同一个原子不可变快照提供，避免热更新时出现“新指纹配旧数组”；单调 Revision 还能识别点集短时间改动后又恢复原内容的情况。
如果一次操作要同时判断“组内有哪些点”和“每个 Source 覆盖哪些点”，还必须使用外层组目录协议：开始先读 `CatalogRevision=C1`，只有 `C1` 为非零偶数才继续；读取组点表、`MemberSourceIds` 和所有成员状态/覆盖清单后，再读 `CatalogRevision=C2`。只有 `C1=C2` 且仍为偶数时，整套结果才属于同一代目录。奇数表示管理器正在热更新，等待后重试；这一步可以防止新组点表与旧成员覆盖表被拼在一起。
SDK 不应持续订阅三个大数组：订阅小标量 Revision、Fingerprint 和 `CatalogState`，Revision 或指纹变化后再按上述协议分页重读。`CoverageKnown=false` 或 `CatalogState=Discovering/CatalogConflict` 时，覆盖结果不是可选依据；冲突来源的清单只作为相对当前可发布组并集的诊断信息，该来源仍不可选择。

### 3.3 已知一个 KKS，怎样知道有哪些来源可切

假设要读取 `ns=2;s=UNIT1_TEMP`：

1. Browse `Objects/RcdManager/Groups` 下的所有组。先读组的偶数 `CatalogRevision`，再按“PointSetRevision 前读 → Count/IndexRange 分页 → PointSetRevision 后读”的协议读取 `PointNodeIds`；包含 `UNIT1_TEMP` 的唯一组就是它的逻辑组。跨组同名 KKS 会被管理器判为目录冲突，所以正常目录中最多匹配一个组。
2. 读取该组 `MemberSourceIds`，得到配置候选，例如 `[lower-a, lower-b]`。
3. 对每个候选读取 `Members/<source>/Selectable`。只有 `true` 才能写入选源。
4. 若只关心 `UNIT1_TEMP`，先确认 `CoverageKnown=true`，再检查它是否存在于该成员的 `ProvidedPointNodeIds`。如果在 `MissingPointNodeIds` 中，该 Source 当前不能提供兼容的这个 KKS。
5. 读完全部候选后再次读取组的 `CatalogRevision`；只有它和第 1 步相同且为偶数才使用结果，否则整套丢弃重读。生产使用优先选择 `Selectable=true`、`CompleteCoverage=true`、`ConnectionState=Connected` 的成员。`Selectable` 是能否写入的最终判断；连接状态只表示此刻在线与否。

`PointNodeIds`、`ProvidedPointNodeIds` 和 `MissingPointNodeIds` 不包含 `_Send` 命令变量或 Method。命令目标还要根据报文中的站址解析，不应把命令节点当普通 KKS 选源。
热删除且仍为兼容性保留的旧 KKS 不再出现在 `PointNodeIds`，直接读取它会得到 `BadOutOfService`。

### 3.4 UaExpert 手工切换步骤

1. 新建连接，地址填 `opc.tcp://<管理器IP>:4840`，连接管理器而不是下级的 `4841`。首次连接按现场证书策略信任管理器证书。
2. 在 Address Space 展开 `Objects → RcdManager → Groups`。找到 KKS 所在组；不确定时把各组 `PointNodeIds` 拖到 Data Access View 查看数组。
3. 展开 `<group> → Members`，比较各 Source 的 `Selectable`、`ConnectionState`、`CompleteCoverage` 和点清单；继续展开 `Ports/Devices` 可确认实际串口与子站。
4. 把该组的 `SelectedSourceId`、`SelectionRevision` 和目标 KKS 都拖到同一个 Data Access View。记录切换前的值。
5. 双击 `SelectedSourceId` 的 Value，按 **String** 写入完整 Source ID，例如 `lower-b`，不要写显示名称、Endpoint 或串口名。
6. 写成功后重新读取：`SelectedSourceId=lower-b`、`SelectionRevision` 增加、`Members/lower-b/IsSelected=true`。现有 KKS 监控项会由管理器分批强制刷新，无需删除再订阅。

UaExpert 的同一连接通常使用同一 Session，所以写入会作用到本窗口读取/订阅的数据。若开了两个 UaExpert 连接，它们是两个 Session，必须分别切换。

### 3.5 客户 OPC 程序的最小流程

```text
连接 opc.tcp://manager:4840，并创建 Session S
  → 从 NamespaceArray 按 URI 找到 businessNS 和 managementNS
  → Browse managementNS: Objects/RcdManager/Groups
  → 对每个候选组 G 读取偶数 CatalogRevision=C1
  → 按 PointSetRevision 前后校验分页读取 G/PointNodeIds，找到包含目标 KKS 的 G
  → 读取 G/MemberSourceIds
  → 按 CoverageRevision 前后校验读取候选的 Selectable、ProvidedPointNodeIds 和状态
  → 再读 CatalogRevision=C2；仅 C1=C2 且为偶数时继续
  → 使用 Session S 向 G/SelectedSourceId 写 String(source_id)
  → 使用同一个 Session S 读取/订阅 businessNS 中的 KKS
  → 读取 G/SelectedSourceId、SelectionRevision、Members/source/IsSelected 验证
```

关键要求：**创建 Write 请求的 Session 必须与 Read/Subscription 的 Session 相同**。有些 SCADA 驱动会为“控制写入”和“采集订阅”各建一个 Session；这样写入只会切换控制 Session，看起来 KKS 没变化。遇到这种情况，应让驱动复用 Session，或对实际采集 Session 使用 Web 的在线 Session 定向选源接口。

### 3.6 切换结果和常见错误

- 写入成功：OPC Write 结果为 `Good`；即使两边当前值相同，也用 `SelectionRevision` 和 `IsSelected` 判断，不能只看数值变化。
- `BadConfigurationError`：Source 不属于该组、目录冲突/不可选，或所选 Source 不存在该 KKS/其类型或归组不兼容。若该点只是本进程内热退役，则读取返回 `BadOutOfService`。
- `BadNotFound`：写入的 Source ID 不存在，或组/Session 中没有对应路由；先重新 Browse，不要继续使用旧配置缓存。
- `BadWaitingForResponse`：该组有 `_Send` 命令等待 ACK；等 `PendingCommandCount=0` 后再切。
- `BadInvalidState`：同一 Session 有并发切源，两个写请求争用了同一 revision；重新读取 `SelectedSourceId` 和 `SelectionRevision` 后只重试一次。
- `BadTypeMismatch`：没有按 OPC String 写 Source ID。
- `BadSessionIdInvalid`：原 Session 已关闭/超时，需要在新 Session 中重新选择；新 Session 从 `DefaultSourceId` 开始。
- 有效但离线的 Source 可以被选择，不会自动切到别处；业务点保留最后值并返回 `BadNoCommunication`。缓存目录离线启动时返回对应类型零值和 `BadNoCommunication`。
- 短暂 TCP/SecureChannel 中断后若恢复并重新附着原 Session，选择保留；CloseSession、SessionTimeout 或管理器重启后清除。
- 若只想单独切一个子站，先在 Web“串口 / 设备映射”中把该子站配置成独立逻辑组。不能在一个已有组里只切一个 KKS，否则同组计算点、命令路由和订阅会失去一致性。

## 4. 日常运维

- **采集**：“下级 OPC → 运维 → 采集”操作串口开关、单站停读。关口释放句柄并影响该口所有站；停读不禁止允许的控制命令。核对期望、已应用、串口打开和实际通信，开关重启后保持。
- **配置**：编辑、校验，再保存到下级。保存自动备份；恢复先载入备份草稿，再确认保存。保存不等于运行生效；显式重启会加载磁盘上全部配置，不只是当前文件，也不会保存未提交草稿。
- **进程**：需先在下级主机运行独立 agent，再在物理来源面板绑定 agent 地址和 instance ID。可 start/stop/restart、查看 PID、退出原因、作业和进程输出；stop 后 agent 仍可接收 start。未绑定或 agent 离线时不能启停。
- **日志**：下级运维日志可筛选、分页、下载当前页，跟随最多 5 分钟；轮转后从尾部重读。进程日志是 agent 保存的固定 stdout/stderr 最新尾部，最多 64 KiB，不替代业务日志。告警、命令与管理审计可追查操作。

agent 必须管理自己启动的 child，不能接管已有 PID。首次先停止目标旧启动方式，固定程序、工作目录和独立持久目录；可使用人工安装的 systemd **用户服务**模板。模板首次不自动拉起下级，确认交接后再 start；未登录开机运行需要现场授权配置 linger。详见 [进程管理部署](lower-process-management.md)。Windows agent 尚未实现、未验收。

## 5. 状态、冲突与备份

- PID running/TCP 连通不代表 OPC 或串口健康；启动后核对来源连接、目录、订阅及点值。accepted/running 不是作业成功，等终态；forced 表示曾强制终止，需检查原因。
- 手动 stop 持久保持 stopped，守护重启后不会擅自拉起。可选 on-failure 只重启该下级，不切换 OPC 来源；systemd 重启 agent 是另一层策略。
- 命令 pending、进程作业处理中或版本冲突时先核对状态。网络断开/unknown 时保留原 request_id 查询和对账，不用新 ID 重复重启；结果确认前相关来源修改可能继续被阻止。
- 旧下级没有 OPC 运维能力仍能供数；独立 agent 进程控制与其能力分开。离线源不自动替换，坏质量旧值不能当新数据。
- 升级前停止相应程序并备份管理器整个 data-dir、agent 状态和下级配置/PKI；导出配置不含密码，也不能替代完整备份。仅在受信任隔离内网使用，安全策略未改变。

本轮远端验证已通过 Rust 全量测试与严格 Clippy、Web 141 项测试和生产构建、Go 全模块 race 与 vet，以及管理端点旧点表/安全策略/Read/Subscribe/命令/Session 恢复/成员树回归。远端实际端口为管理 OPC `4840`、原 Rust 下级 `4841`、两个联调下级 `4874/4875`，旧管理测试端口 `4876` 已释放。systemd 正式安装、Windows、20×5300 点满负载及 24 小时稳定性仍未验收。

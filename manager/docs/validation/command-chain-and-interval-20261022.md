## 网页设置

下级 OPC → 目标来源的“运维” → 配置 → `config.toml` → 参数设置 → “控制命令最小间隔(ms)”。填写整数，依次生成草稿、校验、保存；保存标明“待重启”，不自动重启。再经明确授权重启目标下级，才应用磁盘上当前完整配置。

参数为 `settings.command_interval_ms`，默认 0、允许 0–60000ms。一个下级的各物理端口独立计时；不同控制事务之间生效，普通轮询、同条重试与 ACK 判定不变。管理端和下级的原期限不因间隔被延长，过长间隔或积压会超时；详细约束见[下级配置说明](../guides/lower-operations.md#控制命令最小发送间隔)。旧下级未提供此参数，不能仅修改文件就宣称运行中已支持。

## 本轮确认并修复的问题

| 问题 | 处理 |
| --- | --- |
| 排队过期先发布通用 Failed、后改 Expired，管理端可能抢先固化错误结论 | 先记录精确过期证据，再发布兼容 ACK 失败；失败通知不覆盖已有 Expired/Unknown 等终态。 |
| 控制完成后先公开终态、随后才释放物理占用，快速管理端可能误拒绝下一条 | 确认本次物理 I/O 结束后先释放维护/端口 permit，再公布完成或失败。等待间隔仍保留在唯一串口 worker，下一条不能绕过。 |
| 下级独立到期看门狗的 Expired 被当作已排空，可继续派发队尾 | 管理端保持 TimedOut/BadTimeout，同时取消该物理端口未派发项；不把定时到期当作串口已结束的证明。迟到结果只补查审计。 |
| worker 取消只清理 FIFO，接收通道中尚未入 FIFO 的命令可能没有结束记录 | 退出时拒绝已接收但未执行的通道命令，释放 permit；待应用运维请求返回明确失败，不执行串口或配置开关。 |
| 前次 ACK 超时、下一次写入失败仍沿用 ack_timeout 错误 | 当前写入失败明确记录 write_failed；每次发送/完整写出计数及尝试原因分别保留。不将写失败误报为单纯 ACK 超时。 |

管理端保持每端口 FIFO、载荷固定、队满拒绝、来源/epoch 固定、维护和选源锁。明确完成的协议失败可以接续下一条；未知结果、失联或独立到期不冒险续发。不增加自动重投，不改变重试次数、轮询间隔、校验位延时或设备 ACK 字节。

## 保留的边界

- `00 50 50` 没有命令编号。软件关联可防串路由和审计误配，不能保证设备物理动作恰好一次或证明动作反馈已改变；ACK 只是协议确认。
- 总期限包含排队，管理端默认 30 秒，关联请求还有短调用剩余预算。已写到串口的报文不能撤回；超时后也不自动换源或补发。
- `_Send` 单变量不能保证上级订阅者收到每条中间状态；逐条结果看独立命令审计，不把“入队成功”当设备成功。
- 未执行现场多管理端连续硬件控制、真实 500ms 设备动作、性能压测、Windows 或长测。本轮不宣称所有异常均已消除。
- 上线需另获当次控制暂停和重启授权，通过现有运维平台升级涉及的管理端及采集；不顺带重启无关组件，不替使用人选择现场间隔值。

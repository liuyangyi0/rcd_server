## 1. 结论与实施范围

同时推进三件事：保留并整理 Rust/Go 业务核心、统一部署运维、统一版本与运行目录。三者互相配合，不需要推倒重写。

执行顺序为：**确定统一软件版本与标准目录 → 版本和路径能力 → 发布与维护互斥 → Ansible 统一编排 → 继续内部重构 → 按需增加 HTTP 运维适配 → 分批软件部署验收**。

前三个改造阶段不更换 Rust—Go 实时数据协议。HTTP 运维迁移是后续独立阶段，不能成为前面发布规范化的前置条件，也不能与目录搬迁同时上线。

编写计划阶段只交付文档。用户随后已授权开始实施，开发及隔离测试按阶段进行；现场部署、服务重启、真实设备命令、提交和推送仍须各自获得明确授权，不能将本计划视为现场操作许可。

### 软件与使用人的责任边界

| 内容 | 责任与处理原则 |
| --- | --- |
| 软件版本、发布包、标准安装路径、服务启动和升级恢复 | 本计划负责统一；同一角色使用指定发布包，组件版本及兼容关系可追溯 |
| 串口参数、站点、CSV 点表、计算规则、分组、默认源等业务配置 | 使用人负责设置与修改；不要求跨机器相同，不与历史配置保持不变 |
| 设备掉线、接线、供电、设备本身故障等非软件问题 | 使用人负责处理；软件如实显示状态和日志，不把全部设备恢复正常作为发布条件 |
| 配置兼容、保存/加载正确性、程序崩溃、并发、OPC/API 异常、升级误覆盖 | 属于软件责任，仍须修复和验证，不能以“配置由用户管理”为由忽略 |

软件升级只保留用户数据，不替使用人判断业务配置应当是什么。配置 revision 用于单次操作的防并发覆盖，不是锁定一份长期配置。配置编辑、串口/站点管理和诊断功能继续提供，但不把替使用人维护配置与排查设备故障纳入本次任务。

旧软件版本和路径无需追溯整理成现场历史档案；只在实际部署时识别当次需要替换的进程、文件、服务及备份位置，防止操作错目标。现有版本不同、路径不同、设备离线，都不是准备统一软件之前必须先解决的问题。

### 不变的业务边界

- 管理 OPC 4840、下级 OPC 4841、Web 8087 保持；现有 agent 地址按实例配置保留。
- 保留旧业务 `ns=2` NodeId、数据类型、访问级别、方法签名及管理端固定命名空间。
- 保留每 Session、每组的选源行为，默认来源和中央计算行为不变；已有自动切源及差异告警按原策略运行，不新增自动回切。
- 采集通信中断时输入归零，计算继续执行并沿实际使用输入传播质量，不把所有坏质量计算输出统一清零。
- 单物理串口唯一 worker；轮询间隔、校验位保护、50 ms 等待配置、ACK 判断及重试次数均不在本计划中调整。
- 命令固化来源、物理串口、Session、epoch；收到有效 ACK 后按现有规则立即结束重试。传输超时不重投、不换源、不换协议再发。
- 审计存储故障继续执行设备控制并报告降级；不以审计故障触发断开、自动切源或停止采集。部署备份失败则停止发布，这与设备控制的降级策略不同。
- 保留现有 Web 登录和 OPC 安全设置，不以新协议名义降低权限或开放任意文件/命令执行。
- 不引入 MQTT、消息中间件、K3s、微服务或两个管理端的主备协调；不迁移到 Fledge/EdgeX，不重写计算引擎。
- 本轮标准化以 Linux 现场为目标；保持原 Windows 源码兼容，不宣称新增 Linux 能力已在 Windows 验收。

## 2. 当前软件基础与需要统一的问题

核对开发线为 `codex/opc-device-groups`，工作目录为 `rcd_server_device_groups`。另一个 `rcd_server` worktree 有自己的未提交修改，不混入本次工作。

本计划依据源码和已有发布记录编写，未重新读取远端状态。正式部署前只核对当次软件替换所需的目标信息，不能照抄历史 PID、目录或服务名直接停程序；不为本次整理重新调查现场业务配置和设备故障。

| 项目 | 已有能力 | 后续需要完成 |
| --- | --- | --- |
| Rust/Go 组件 | 已拆出命令、计算、冗余、连接、站点、日志等部分组件 | 来源状态、目录索引、共享配置锁和 Rust 剩余职责继续收口 |
| 发布工具 | `tools/release/release.py` 已有预检、构建、校验、备份、发布、回滚 | 正式版本注入、agent 独立角色、systemd 系统级适配、跨入口维护互斥及完整日志 |
| 命令追踪 | `command_tracking`、下级 SQLite、独立实例与启动身份、增量补查 | 保持并补齐验收，不重做一套命令协议 |

| agent | 与管理端共用 RcdManager 构建产物，可独立运行 | 角色分别发布、分别显示实际运行版本，避免管理端升级隐含升级 agent |
| 服务所有权 | 46 记录为 agent 管理 child；30/58 有系统级下级服务 | 核实每个实例真实拥有者，不允许 systemd 与 agent 同时拉起同一下级 |
| 文档 | 有当前架构及多轮历史记录 | 部分运维文档仍含早期端口、版本和“未部署”叙述，需要明确历史范围 |

最近记录中的部署角色为：30 只有下级及已有 agent；46、58 各有管理端、下级及已有 agent。agent 在最近升级中未重启升级。两个管理端独立运行，不是共享状态的高可用集群。

本计划不列站点故障清单，不以正常站点数量作为软件升级放行条件。软件部署状态与设备通信状态分别展示；软件已正常部署不表示物理设备已经恢复。

## 3. 目标责任边界

| 层次 | 保留或采用的实现 | 唯一职责与约束 |
| --- | --- | --- |
| 物理采集 | Rust 下级 | 串口唯一读写者、轮询、ACK、版本事务、实际采集状态 |
| 业务管理 | Go 管理端 | 来源/目录、Session 路由、计算、控制关联、告警及 Web API |
| 独立运维代理 | 现有 Go agent | 固定实例启停、状态、维护栅栏；以后可代理限定的运维请求，不解析串口报文 |
| 服务管理 | 现有 systemd | 按登记的单一拥有者模型拉起进程，保持开机自启 |
| 单机发布 | 现有 release 工具 | 精确目标、备份、停止、原子安装、验收、恢复；只有这一套实现替换/恢复规则 |
| 多机编排 | Ansible | 选择主机、传输已验证产物、顺序调用 release 工具、汇总结果 |
| 运维任务入口 | Semaphore UI，可后装 | 展示并执行上述固定任务，不另写发布引擎，不替代业务 Web |

Ansible 通过 SSH 执行运维任务，Semaphore 提供任务模板、主机清单和 Web 入口；二者均不进入实时数据路径。相关能力见 [Ansible 官方仓库](https://github.com/ansible/ansible)、[Semaphore 官方仓库](https://github.com/semaphoreui/semaphore)。控制节点停止时，采集、OPC、计算和既有服务守护必须继续运行。

Ansible 不成为现场业务配置的第二个主人：它可以管理程序、服务模板、环境路径和部署清单；不能每次发布就用模板覆盖 Web 已保存的 `config.toml`、CSV、计算配置、数据库或站点状态。首次初始化配置是另一个显式任务。

## 4. 阶段 P0：确定统一软件发布版本与标准目录

### 实施事项

1. 确定本次软件源码快照与目标 release_id，包含有效的未提交修改；保留用户说明和历史包。没有提交授权时不提交或推送。
2. 明确发布包包含下级、管理端、agent 哪些角色；同一角色在不同机器安装同一指定版本，业务配置独立保留。统一版本不等于给不同组件伪造相同的二进制身份。
3. 确定标准程序、配置、状态、PKI、日志和备份目录，补齐显式路径能力。旧版/旧目录在升级时兼容处理，不要求先手工统一。
4. 固定用于软件回归的测试输入和接口契约：OPC NodeId 生成规则、Session 行为、计算语义、命令与错误处理。这些是隔离测试用例，不是禁止使用人修改现场点表或计算规则。
5. 真正部署时，仅临时核对目标服务、实际进程/文件、运行账户和需保留的数据位置，生成本次安装与恢复记录；不收集整套现场配置/设备故障基线。

### 交付与通过条件

- 交付目标发布包清单、标准目录规范和软件兼容测试清单；不交付现场设备故障整改清单。
- 同一软件版本支持各机器不同且可继续修改的业务配置；不将密码、私钥、数据库及现场配置正文加入 Git。
- 当次替换必须识别唯一进程拥有者，避免双启动；这是部署安全检查，不要求长期维护所有旧版/旧路径档案。

## 5. 阶段 P1：统一版本身份与显式路径

### 5.1 构建与运行身份

Rust、Go 管理端和 agent 统一提供只读构建信息：

- `release_id`、组件角色、应用版本、Git 起点提交、源码摘要、脏快照标记、构建 UTC 时间、目标平台。
- 协议版本、feature 列表及支持的数据库 schema 范围分别记录，不能仅比较应用版本字符串判断兼容。
- `version --json` 不启动采集、数据库迁移、OPC 或 HTTP；旧 `version` 文本输出保持可用。
- 管理 Web 展示管理端、各下级、各 agent 的独立运行版本、启动时间和报告时间；离线显示最后记录及过期标记。
- 程序内版本来自编译注入；实际二进制 SHA-256 由发布/检查工具验证，不能把磁盘新文件的 hash 当成旧进程的 hash。

正式发布拒绝 `unknown` 构建提交和未记录的工作区。允许明确标记的测试快照，但必须保存完整文件清单、源码摘要及产物摘要，不伪装成干净提交。

构建清单与目标部署清单分开：同一份 46 构建产物可以部署到多个兼容主机，每台生成自己的部署记录，不改写原始构建身份。先核对 CPU 架构、动态库/ABI 和最低运行环境，不能只凭 SHA 相同判断可运行。

### 5.2 下级显式路径

新增集中解析的运行路径对象，覆盖配置、状态、PKI、日志和实例锁：

- 建议参数：`--config-dir`、`--state-dir`、`--pki-dir`、`--log-dir`；显式参数优先于相应环境配置，最后才使用旧版默认路径。
- 所有参数缺省时，保留“实际 EXE 同级 config”等现有行为，不改写 `RCD_CONFIG` 的既有含义。
- 同一个路径对象提供给采集、计算、Operations、版本、命令审计、日志和 OPC 启动，不允许各模块分别猜目录。
- `operations.json`、`station_versions.json`、命令审计库及其稳定身份迁入 state-dir 时保留内容和 revision；未显式设置时继续使用旧位置。
- 实例锁不随二进制版本改变，旧目录锁与新目录锁不能成为同时运行两份程序的漏洞。物理串口独占检查作为第二道保护，不通过删锁解冲突。
- 对显式指定但缺失/无权限的配置目录报错，不回退到另一套配置或自动生成空配置。

### 5.3 建议的 Linux 目录布局

以下是待验证的目标布局，不代表当前已搬迁；实际运行账户和权限沿用各机器已批准配置。

```text
/opt/rcd/
  releases/<release_id>/       不可变产物、manifest、校验清单
  bin/rcd_server               下级固定入口
  bin/RcdManager              管理端固定入口
  bin/RcdAgent                agent 固定入口，可来自同一 Go 构建
/etc/rcd/                     服务环境文件与明确路径，不放实时状态
/var/lib/rcd/
  lower/<instance>/config/     config.toml、calc.toml、CSV；业务用户可修改
  lower/<instance>/state/      开关、版本、命令审计、持久身份、实例锁
  lower/<instance>/pki/        原证书与私钥
  manager/<instance>/          管理数据库、原 PKI 等
  agent/<instance>/            agent 状态、作业及维护记录
/var/log/rcd/<role>/<instance>/
/var/backups/rcd/<deployment_id>/
```

第一轮采用固定普通文件入口、同文件系统临时文件加原子替换，不依赖修改 `current` 链接触发 agent 自动采用新程序。当前 agent 会在启动时解析符号链接，单改链接可能继续使用旧目标。

manager/agent 即使来自同一二进制，也使用独立安装入口和服务配置，升级其中一个不默默更换另一个。历史目录先保留作回滚依据，禁用旧启动入口并记录，不直接删除。

### 通过条件

- 使用同一份隔离测试配置验证旧/新路径行为一致；实际迁移保留当时用户配置、稳定身份、PKI 和状态，不要求现场 NodeId、规则数量或配置 revision 永远不变。
- CLI、运行 API、发布 manifest 与实际 PID 映像身份一致；不能只核对入口文件。
- 分别验证工作目录改变、路径空格、权限不足、符号链接、配置缺失及重启；新旧目录不会双启动。
- 本阶段先发布路径能力，目录搬迁在后续独立维护窗口完成。

### 5.4 用户配置不被软件发布接管

- 程序包不包含可直接覆盖现场的业务配置；示例放独立 examples 目录。首次创建默认配置必须是明确的初始化动作，只创建不存在的文件。
- 普通软件升级不改串口参数、站点、点表、计算规则、组策略或来源选择，不跨机器同步这些内容。
- 目录迁移复制迁移当时的最新数据，不从早期测试包或“基线配置”恢复。校验摘要仅用于证明本次复制完整，不作为长期配置一致性要求。
- 用户在准备期间修改配置是允许的；迁移提交前若内容变化，重新读取或提示重试，不用旧快照覆盖。仅实际复制/切换的短窗口协调写入，不能从计划到上线长期冻结编辑。
- 迁移后用户继续通过原有 Web/受支持的文件方式修改配置。配置格式有升级需要时另做显式兼容迁移，不顺带改变配置业务含义。

## 6. 阶段 P2：统一维护互斥与发布执行器

### 6.1 一个物理实例只能有一个进程拥有者

先保留各实例现有拥有者模型，release 工具明确适配 `systemd-system`、`systemd-user`、`agent-child`，不做自动猜测或自动接管 PID。

如需 Web 管理已由 systemd 直接运行的下级，再为 agent 增加启动配置固定的 `systemd_unit` 后端；仅调用指定 unit，不能再 fork 第二个 child。旧 `owned_child` 模式保持兼容。后端选择不能通过普通 HTTP 请求改变。

期望状态、人工停止后的开机行为、异常自动拉起、权限及停止超时均须有明确映射和回归测试，不能只把 start/stop 命令换成 systemctl。迁移拥有者与搬目录分开执行。

### 6.2 发布维护栅栏

“部署工具锁住自己”不足以阻止 Web、另一管理端或直连 OPC 客户端发命令。新版本须在目标物理实例建立共同检查的维护栅栏：

agent 是实例维护作业的唯一权威，Rust 是命令准入与串口排空的唯一权威；二者用同一 token 明确握手，不宣称跨进程原子事务。仅在 agent 已登记持久作业、Rust 已持久确认阻止新请求且待执行事务清零后，允许发布继续。任一方状态未知或 token 不一致都保留阻止状态、先对账。下级准入状态不得仅放进程内存，以免重启后出现空窗。

本阶段在现有 Operations schema v1 上增加明确的维护能力和握手动作，agent 使用现有进程管理通道；不提前引入 P5 的通用 HTTP 运维迁移。物理绑定校验 gateway 实例与 agent 实例的对应关系，不把 IP、显示名或单个管理端 source_id 当成全球唯一设备身份。

1. 以 `deployment_id + physical_instance_id` 建立持久维护记录，包含目标、发起者、阶段、版本和 fencing token。
2. Rust 在进入维护时原子关闭新增命令/运维修改准入，覆盖旧 `_Send`、旧 Method 和关联命令入口；已经接受的事务继续完成。读取、订阅和采集仍可运行，直到明确停止程序。
3. 版本查询等有副作用事务同样纳入排空；不得由另一个入口绕过。
4. agent 的进程动作、Web 修改、发布器必须遵守同一维护状态。管理端自己的锁只是友好预检，目标实例才是最终拒绝点。
5. 检查 46、58 已登记管理端及下级实际 pending，全部清楚且已排空后才能进入停止/备份阶段。维护中的拒绝使用现有兼容的 busy 状态，Web 返回 409 并说明维护目标。
6. 网络断开、发布器退出或租约过期，不能自行清除“替换中/结果未知”的持久栅栏。恢复后凭原 deployment_id 对账；旧持有者不能操作或解除新栅栏。
7. 下级重启必须仍识别维护状态，验收完成后由明确的收尾操作释放。维护期间不自动重发曾经失败或未知的设备命令。

排空期限依据当前已接受事务的既有截止时间配置，不修改设备重试时序。超过期限而结果仍未知时停止发布、保留现场，不通过强杀或删除 pending 来制造“已排空”。具备 root/直接 SSH 权限的旁路操作不受业务 API 栅栏完全约束，仍需维护窗口纪律；不能宣称它是操作系统级防绕过机制。

这不是双管理端选主或 HA。只协调对一个物理实例的破坏性运维；不改变平时业务采集与两管理端并行读取。

旧下级不支持维护栅栏时，继续要求人工确认所有相关入口已暂停控制，并标记为人工保障模式；不宣称已实现机器强制互斥。无法确认直连客户端状态时不得自动发布。

### 6.3 改进现有 release 工具

- 保留现有预检/构建/校验/备份/部署/验收/回滚流程，不在 Ansible 中复制一套安装算法。
- 显式目标扩展到主机、组件角色、实例、服务范围和产物 ID；58 不因“升级管理端”而默认被包含。
- 分开软件身份、配置 revision、数据库 schema、进程 boot ID 与物理实例 ID。
- 所有成功和失败步骤均保存 stdout/stderr、开始/结束时间、退出码；输出机器可读阶段结果，并对秘密脱敏。
- 阶段状态持久化：预检、已暂存、维护中、已停止、已备份、已安装、启动中、验收、成功/失败/未知。
- 重入先读取原记录、实际文件与进程状态，不自动重做 restart、restore 或设备动作。只读状态查询可重试，破坏性动作不能被编排工具的重试机制重复执行。
- 校验目标磁盘空间、备份完整性、运行账户权限、串口唯一拥有者、旧版可用产物和恢复路径。
- 对本次操作涉及的数据做保护性一致备份，涵盖所需 agent 状态、命令审计库、数据库、配置、PKI、身份和服务环境文件；备份是防丢失，不代表冻结或校正现场配置。日志不因升级清空。
- 数据库迁移保持追加结构；旧二进制不能读新 schema 时，不能直接换旧程序，也不能默默恢复旧库覆盖用户后来修改。保全当前数据，说明恢复影响，并按明确授权的恢复范围执行。

### 通过条件

- 两管理端、Web、部署工具、直连旧 OPC 入口的竞争在最终物理目标处被正确拒绝。
- 停止未确认、备份失败、产物不符、维护结果未知、跨主机错配均不能进入下一步。
- agent 升级是否连带下级停止必须按其拥有者模式明确展示，不把它当成无影响更新。
- 回滚演练包含数据库、身份和审计恢复，不只演练二进制替换。

## 7. 阶段 P3：Ansible 编排与 Semaphore 入口

### 7.1 仓库组织

新增 `deploy/ansible/`，仅存模板和无秘密示例：

- `inventory.example.yml`：主机角色、实例、服务拥有者、目标路径和组件清单。
- `requirements.yml` 及控制节点依赖锁：固定实施时已验证的 Ansible/collection 版本，不使用浮动 latest。
- `playbooks/inspect.yml`：只读检查目标软件、服务和软件健康，不收集或整改设备故障。
- `playbooks/stage.yml`：分发已验证包并核对摘要，不替换运行程序。
- `playbooks/deploy.yml`：显式目标、串行调用发布工具。
- `playbooks/verify.yml`：目标软件版本/路径、启动、OPC/API 和软件数据处理行为验收，不以设备全部在线为条件。
- `playbooks/rollback.yml`：显式指定部署记录和一致性备份。
- `roles/rcd_release/`：共用任务；初始化目录/服务另有显式任务，默认不修改现有业务配置。

真实 inventory 与凭据放在 Git 外的受控目录或凭据存储；不将现有密码写入 playbook、示例或任务输出。

### 7.2 编排规则

- 控制任务、构建和测试均从 46 的隔离环境执行；30、58 接收同一份通过兼容检查的产物，不现场重建。
- 预检可并行；有停机影响的阶段每次只操作一个明确实例，初始采用 `serial: 1`。软件发布失败或操作结果未知时停止后续主机；设备离线或非软件故障不按发布失败处理。
- 保留用户给定目标列表，不提供默认部署 all 的快捷任务；每次预览列出主机、组件、预计影响、备份和目标版本。
- 启停只由 release 工具执行；Ansible handler 不另做一次 restart。
- 同一版本重复 inspect/stage 应无破坏性变化；check mode 仅是预览，不能被当成现场发布成功。
- 46 同时作为控制节点和业务主机时，任务不依赖待重启的管理端进程存活；执行状态落在独立目录，可在连接恢复后对账。

Ansible 的批次和失败传播能力采用官方机制，但我们的维护栅栏、软件功能验收和数据库恢复仍由项目实现。[批次策略](https://docs.ansible.com/projects/ansible/latest/playbook_guide/playbooks_strategies.html)、[错误处理](https://docs.ansible.com/projects/ansible/latest/playbook_guide/playbooks_error_handling.html)。

### 7.3 Semaphore

Ansible 命令行任务先验收，再安装 Semaphore；它不是发布正确性的前置条件。

- 初始只提供盘点、暂存、单目标升级、验收和指定备份回滚模板。
- 维护任务需要明确目标和当次授权；不安排无人批准的定时升级，不提供任意 shell 执行入口给业务操作员。
- 记录操作者、模板版本、目标、release/deployment ID、结果和证据链接。
- Semaphore 账户、监听位置和凭据配置单独登记，不修改现有业务 Web 账号或 OPC 安全策略，不默认沿用业务初始密码。
- 入口不可用时允许授权运维人员执行同一 Ansible 任务；不因此停止业务，也不另加自动故障转移逻辑。

### 通过条件

三台主机同一角色能统一到指定软件版本及标准路径；单目标更新不触碰其他主机或非目标组件、不覆盖用户配置；软件发布失败会阻止后续目标，设备故障不作为阻断条件；恢复任务不重复执行破坏性动作。

## 8. 阶段 P4：完成必要的内部架构整理

不按文件长度追求拆分数量，按“谁拥有可变状态、谁能提交修改、锁保护什么”验收。

### Go 管理端

- 来源连接和来源状态：在已有 `sourceConnections` 基础上明确状态快照与代次校验，旧连接不能提交新状态。
- 目录：收口目录索引、隔离原因与发布状态，防止多个组件各维护一份不同的目录真相。
- 配置协调：保留必要短事务；耗时扫描、网络调用和文件操作取快照后在锁外执行，提交前复核 generation/revision。
- 命令：端口占用仍由 RouteTable 唯一负责；命令服务负责派发、终态与补查，审计只负责保存，不拥有第二套 pending。
- 计算、冗余、站点、日志沿用已有组件，补齐生命周期、队列上限、取消、关闭与失败可见性，不为统一风格重写成熟路径。
- HTTP/OPC 适配器使用领域请求/响应，业务组件不继续依赖页面展示类型。

### Rust 下级

- 保留 transport、command_transaction、version_transaction 已有拆分，继续从 worker 中抽取恢复、轮询调度和错误统计的独立职责。
- 普通轮询、控制 ACK、版本帧保持独立解析与时序边界；不得新增第二个串口读取者。
- Operations 作为共同业务入口，OPC 和未来 HTTP 只做协议转换。
- 先补行为测试，再移动逻辑；物理时序、串口重试与 TCP 编码必须保持。

### 补丁依赖与契约

- 为 Rust/Go OPC 本地补丁维护上游基线、修改理由、对应测试和可移除条件。
- 依赖升级与业务重构分开发布；普通管理端全包测试不能替代独立 fork 模块测试。
- 在已有 `contracts/command-tracking/v1/` 基础上补版本、维护和运维契约；保留黄金样例，Rust/Go/TypeScript 分别验证。
- 未知可选响应字段允许扩展；未知动作、破坏性版本、身份不符、非法 revision 和超限内容必须拒绝。

### 通过条件

组件状态只能通过其方法修改；无第二份端口占用、来源身份或目录权威状态；网络和文件 I/O 不在组件共享状态锁内；Go race 与相关 fork 回归通过，同一测试配置生成的黄金点表不变，不锁定用户现场点表。

## 9. 阶段 P5：运维 HTTP 适配，独立开关、后续实施

### 9.1 哪些不迁移

| 内容 | 本计划处理 |
| --- | --- |
| Rust 到管理端的数据、质量、时间戳和订阅 | 保留 OPC UA |
| 管理端到客户的业务数据、选源、写入和 Method | 保留 OPC UA |
| 管理端到下级的设备命令及 CommandRevision/结果补查 | 保留现有 command_tracking OPC 通道及旧版兼容路径 |
| 下级普通日志推送 | 保留现有 HTTP 协议、去重与序号规则 |
| 启停/升级 | 独立 agent 与发布工具，不让 Rust 自己重启自己 |

HTTP 运维不是为了解决实时数据性能，也不能消除设备 ACK 没有命令编号的限制。没有充分收益时，本阶段可以停在统一业务接口和契约，不影响 P1–P4 交付。

### 9.2 如实施，采用单一业务实现、两个适配器

建议使用现有 agent 作为固定外部运维入口；Rust 新增默认关闭的本机 HTTP 运维适配，绑定回环地址。agent 仅向安装时配置的本机目标转发白名单操作，不接受客户端传任意 URL、可执行文件或路径。

- 不新增 Rust 对外公网卡监听；本机端口在部署 profile 中明确分配并检查冲突，不改变 4840/4841/8087。
- agent 不自行编辑 Rust 业务文件，不解析串口，不复制校验/保存逻辑。Rust 的 Operations 服务是唯一修改者。
- 下级未运行时，配置读写等需要 Rust 的动作返回 unavailable；agent 仍能提供启停和作业查询。不为了“停机也能改配置”再增加另一套写入器。
- 旧 OPC Operations 保留，旧管理端继续可用；新管理端按能力和显式绑定选择 HTTP，不根据版本号猜测。
- 新监听和代理鉴权必须与现有受信任边界匹配，且经过检查；实例 ID 仅防错目标，不作为身份认证。不满足访问控制要求时保持功能关闭。

### 9.3 分批迁移的功能

1. 只读：能力、软件版本、运行状态、配置列表/正文及文件版本。
2. 配置：校验、保存、日志等级、计算 local/manager 模式；保留保存后待重启语义。
3. 采集控制：串口开关、站点停读、模块类型与版本查询；仍在串口 worker 安全点执行，未知/俄供站点仍禁止查询。

下级日志推送不重做；旧 OPC 日志读取保留为兼容入口。每批只迁一种能力，不能同时改调用协议、规则语义和目录布局。

### 9.4 契约和错误处理

- 管理 Web 对外 `/api/v1/sources/{id}/operations/...` 尽量不变；内部增加运输适配，不让页面感知两套业务规则。
- 校验 `source_revision`、绑定版本、目标 gateway/boot identity、资源 revision 与 `If-Match`；这些版本各自有作用域，不能混用。
- 变更固定 request_id、请求摘要、目标和截止时间；相同 ID/内容返回原结果，不重新执行；内容不同返回冲突。
- 有副作用请求的接收记录与结果查询能力必须先完成。持久证据不可用时，HTTP 运维修改拒绝受理；这不改变设备命令“审计失败继续控制”的既有策略。
- 不重复设备命令 payload；本阶段的配置/运维 request_id 与已有 command_id 保持独立语义。
- HTTP 请求超时、无效响应或确认丢失后只查原结果，不回退 OPC 再执行。只在派发前已确认“不支持此能力”时选择兼容通道。
- 查询结果丢失/过期不表示未执行；重新读取资源版本并保留“结果未知”，不能自动用新 ID 重做。
- revision 冲突/忙碌 409，缺前提 428，输入超限 413，无效配置 422，来源服务不可用 503；传输超时 504 不能伪装成确定失败。
- 所有页数、字节上限、日志代次、配置白名单与审计脱敏继续保留。

### 通过条件

旧管理端+新下级、新管理端+旧下级、新新 HTTP、两管理端跨协议并发均通过；相同资源在 OPC/HTTP 上使用同一 revision 和互斥规则；故障注入确认没有跨协议重复写入或重复查询硬件。

HTTP 上线不立刻删除旧接口。只有全部现场组合验证、旧客户端依赖核查和独立下线授权后，才另行讨论废弃范围。

## 10. Web 可见性与操作体验

在现有系统/来源/进程页面增加必要信息，不再新造一个与 Semaphore 重复的发布平台：

- 管理端、下级、agent 的运行版本、构建提交/快照、启动时间、连接和上报时间。
- 部署中的目标、阶段、操作者、维护原因及是否阻止命令/修改；结果未知时显示核对入口，不显示自动重试按钮。
- 区分“文件已更新，进程未重启”“进程已运行”“OPC 已连接”“物理采集正常”。
- 显示正在使用的运维通道、能力兼容状态和脱敏运行路径；细节按需加载，不暴露凭据。
- 发布历史可链接到相应任务和摘要；不能把普通业务管理员自动提升为主机发布管理员。
- 沿用分页、筛选、相关 SSE 失效，避免版本/发布信息频繁刷新整个点表。

UI 不声称两管理端自动同步配置；46 和 58 的分组、默认源、计算与账号数据库仍独立。

## 11. 测试与性能验收

所有构建、可执行测试、race、前端测试、浏览器和验收客户端都在 46 执行。30/58 仅在授权阶段接收产物并进行目标服务操作；本机只改源码/文档、检查差异和传输文件。

### 功能矩阵

| 类别 | 必测内容 |
| --- | --- |
| 版本/路径 | 旧路径兼容、显式目录、缺权限、用户配置不被覆盖、迁移期间配置变更保护、运行映像与入口不一致、manager/agent 分别升级 |
| 身份/数据 | manager/gateway/agent 身份不变、boot ID 正确改变、PKI 保留、命令游标与历史、站点版本恢复 |
| 服务 | system/user/agent-child、单一拥有者、停止保持、异常拉起、agent 重启影响、整机自启 |
| 发布 | 错目标、坏摘要、空间不足、备份失败、SSH 断开、任务恢复、重复执行、部分主机失败、回滚 |
| 维护 | 双管理端与直连命令竞争、旧入口、待执行命令排空、旧 token、进程重启后未知栅栏、恢复释放 |
| OPC/业务 | 固定测试配置的黄金点表、用户改点表后的正常重建、Read/Write/Call/Subscribe、Session 独立选源/恢复、同值切源、默认源计算、断线归零、自动切源语义不变 |
| 命令 | 首次/第二/第三次 ACK、立即停止补发、串口打不开、部分写出、超时/迟到结果、重启未知、无自动重投 |
| HTTP 若启用 | 跨协议 CAS、重复 ID、能力降级、超时补查、旧版兼容、下级停止、伪目标/任意路径/越界请求拒绝 |
| 日志/Web | 推送去重、查询与轮转、准确分页、维护状态、未知结果、脱敏、桌面/窄屏及浏览器错误 |

确定性输入、桩和故障注入用于软件逻辑回归，报告中明确标注，不宣称真实设备正常。现场设备联调不作为本次软件版本/路径统一的前置工作；若后续另行要求，必须确认具体主机、端口、站点、报文及预期反馈，不自动选择任意报文测试。

### 软件部署验收与设备状态分开

- 发布验收检查目标软件版本、规范路径、进程、配置加载/错误提示、数据库兼容、Web/OPC/API 以及软件处理逻辑；不要求业务配置与历史相同、不要求物理设备全在线或点值全部 Good。
- 设备故障仍如实展示给使用人，但不因此自动回滚软件。不得直接用混合了设备故障的全局健康布尔值作为唯一升级成败判据。
- 若用户配置本身无效，软件应给出明确错误，使用人负责改正；报告分别写“软件已安装”和“配置待使用人处理”，不能伪称业务就绪，也不自动覆盖配置。
- 原本受支持的合法配置因新软件不兼容而无法加载、升级丢数据、崩溃或错误生成点表，属于软件缺陷，必须修复，不能推给使用人。
- 无法判明原因时保留“待确认”和必要软件日志，不把所有通信异常直接归为硬件问题；本任务不展开设备维修排查。

### 性能与稳定性

- 固定隔离性能测试的输入负载和采样/发布设置，不为通过测试而延长采样周期；这不限制使用人修改现场配置。
- 保留目标：下级数据进入管理端到上级通知 P95 ≤500 ms；中央计算批次 P95 ≤50 ms。
- 测量时分别记录 OPC 接收、缓存/计算、通知各阶段；跨机时间差需校准或采用可关联测量，不能把不同机器的未校准时间戳直接相减。
- 20×约 5300 下级监控项、10 个上级全量订阅属于容量验收；现场三来源测试不能代替这一规模。非真实设备负载须单独标注。
- 观察 CPU、RSS、goroutine/线程、队列水位、软件重连行为、日志积压、审计降级和命令补查；不建立设备故障变化考核或要求修复离线站点。
- 一小时稳定性通过后，再做一夜真实运行检查；未完成就列为未验收，不把已启动测试写成通过。
- Go 相关包与独立 OPC fork 执行 race；Rust、Web 和 release/Ansible 检查按批次风险运行。仅文档变动不触发全量程序重建。

## 12. 现场发布、目录迁移与回滚

### 发布批次

1. 先在 46 隔离环境完成实现与恢复演练，不争用现场串口。
2. 发布兼容的版本/路径能力，仍在旧目录运行；不同时搬目录或切 HTTP。
3. 在支持维护栅栏的版本上启用新发布流程；旧版本用已明确确认的人工维护窗口。
4. 经授权，逐个迁移目录/服务入口，保留当时用户配置与必要备份；目标选择依据软件角色和维护窗口，不要求先修好设备或取得“全部采集正常”的基线。
5. 46 和 58 管理端分别发布，不能同时停两台；下级每次一个，agent 另列组件并说明是否影响 child。
6. 后续单独启用只读 HTTP，再启用每类修改能力；不与第一次目录搬迁同批。

迁移会影响选中该来源的客户端：手动固定的 Session 可能暂时坏质量；已有自动策略可能按其配置切换；中央计算取决于默认源。发布工具不能偷偷修改默认源或强制所有 Session 切源。维护预览须列出这些影响。

### 单目标流程

明确目标与授权 → 最小软件目标预检 → 校验暂存包 → 建立维护栅栏并排空 → 停止且确认串口释放 → 保护性备份 → 安装或迁移 → 启动 → 核对实际软件版本/路径/身份 → 软件功能验收（设备状态独立显示）→ 释放维护 → 保存报告。

### 回滚规则

- 每阶段有独立备份和回滚说明；软件升级、目录迁移、拥有者迁移、HTTP 启用分别可回退。
- 回滚前保存失败版本及其数据库、命令审计和日志，防止新产生证据被覆盖。
- 默认只回退软件，保留使用人当前配置与数据，不因软件回滚恢复一份旧业务配置。
- 旧软件无法读取当前数据库时，停止自动回滚，保全当前数据并说明兼容与恢复选择；只有明确确认覆盖范围和可能丢失的后续修改后，才恢复配套一致性备份。不承诺无损降级。
- 保留物理实例 ID、manager ID、证书和运维绑定。不能复制 46 的整库到 58 来“统一配置”，否则可能复制管理实例身份和独立状态。
- 回滚不得让历史 Accepted/Executing 命令重新入队；未知结果继续未知，只读核对。
- 停止未确认、备份损坏、恢复范围不明时，保持明确的失败/维护状态并请人工决定；不擅自强杀、不删锁、不循环自动回滚。

## 13. 里程碑与交付物

| 里程碑 | 可独立交付的结果 | 放行条件 |
| --- | --- | --- |
| M0 | 统一目标软件版本、发布包与标准目录规范 | 源码快照可追溯，配置/设备责任分离，不要求先整理现场历史 |
| M1 | 真实版本显示、产物清单、显式路径能力 | 旧路径兼容、身份不变，用户配置保留且可继续修改 |
| M2 | 维护互斥、发布工具升级、回滚演练 | 竞争/超时不越过边界，备份恢复可核验 |
| M3 | Ansible 任务与规范目录试点 | 单目标可重复执行，软件发布失败停止后续主机，设备故障不作发布门槛 |
| M4 | 组件状态边界与补丁清单 | 关键并发/业务回归及性能基线通过 |
| M5 | 可选 HTTP 只读，再分批写入 | 跨协议契约、互斥、结果未知均通过 |
| M6 | 分批软件升级、说明、稳定性报告 | 每个授权目标的软件独立验收，不冒充设备验收，未覆盖项如实列出 |

M1–M3 是优先交付范围；M4 按组件分批，不阻塞已经完成的发布规范化；M5 独立决定是否启用。Semaphore 在 Ansible 任务稳定后安装，不是完成 M1–M3 的必要条件。

最终交付包括：源码与契约、无秘密部署模板、版本/路径说明、逐组件升级回滚手册、实际验收证据、补丁依赖台账、运行版本清单和剩余风险。

降低维护成本的检查标准不是“文件更少”，而是：能可靠识别每个运行版本、同一件事只有一个实现和状态拥有者、升级不靠临时脚本拼接、故障可以按记录恢复、不同协议不会重复执行业务操作。

## 14. 实施时需要确认的操作项

计划采用上述推荐方向，无需为编写或只读审查反复提问。涉及以下动作时，再取得当次明确决定：

- 具体要部署的主机和组件、控制暂停窗口、允许的短时中断与回滚范围。
- 建立 `/opt`、`/etc`、`/var` 目录或改变 systemd 服务拥有者所需权限；不能顺带改变运行账户或串口权限。
- Semaphore 的安装位置、账号与凭据配置；若暂不安装，先使用同一套 Ansible 任务。
- 真实命令验收的明确目标和报文。
- 提交、打标签、推送与旧目录清理；上述操作均不包含在“写计划”授权中。

## 15. 计划编写阶段的核对与边界

- 已只读核对活动 worktree/分支、已有未提交修改、架构记录、下级 Operations/agent 边界、配置路径解析、构建信息及发布工具入口。
- 已对照 Ansible/Semaphore 官方资料核对工具职责和批次/失败控制能力；未固定尚未在现场验证的具体工具版本。
- 编写阶段仅修订本计划和文档导航；删除现场配置/设备故障基线要求，明确用户配置持续可改与软件验收边界；当时未修改程序、部署模板、现场配置或服务。
- 编写阶段只检查文档，没有运行程序测试。后续开发和测试结果记录在 [标准化第一批实施记录](../../manager/docs/validation/standardization-p1-validation.md)，不得将局部通过写成整个计划已经完成。

后续进展（2026-09-28）：Ansible 已从只读巡检扩展至分发、串行部署、软件验收及显式回滚/恢复；96 项发布工具测试、8 项 Ansible 检查与真实 Go agent/Rust OPC 隔离互操作通过。边界与证据见 [Ansible 发布编排验收](../../manager/docs/validation/ansible-release-validation.md)。这不表示 Semaphore 已安装、现场已升级或全部里程碑已验收。
